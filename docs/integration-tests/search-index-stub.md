# 🧪 Search Index Stub for Integration Testing

Our `UseCase` tests interact with Azure Search. Unlike [CosmosDB](./cosmosdb-docker-emulator.md),
Azure Search has **no local emulator**, so it has to be stubbed.

The stub is **in-process**. It requires no container, no server, no port and no certificate, so the
search integration tests run anywhere `dotnet test` runs.

---

## How it works

`AzureSearchIndexStub` (in `DfE.GIAP.SharedTests`) holds a response payload per index name and
exposes an `HttpMessageHandler`. That handler is installed as the Azure SDK's transport:

```csharp
new SearchClient(
    endpoint, indexName, credential,
    new SearchClientOptions { Transport = new HttpClientTransport(handler) });
```

A test opts in before registering the search feature:

```csharp
services
    .AddStubbedSearchIndex(_searchIndexStub)   // must come first
    .AddSearchCore(configuration);
```

`Dfe.Data.Common.Infrastructure.CognitiveSearch` registers its `ISearchByKeywordClientProvider` with
`TryAddSingleton`, so a provider registered beforehand is left in place. `AddStubbedSearchIndex`
supplies `StubSearchByKeywordClientProvider`, which mirrors the package's own provider — same
per-index client caching, same `SearchByKeywordClientInvocationException` for an unconfigured index —
differing only in passing `SearchClientOptions`.

Response payloads live in `DfE.GIAP.Core.IntegrationTests/contracts/` and are plain Azure Search
response bodies, copied to the test output directory.

### What is still real

Everything above the transport: request construction, the
`/indexes('{index}')/docs/search.post.search` route, `SearchOptions` serialisation, the wire JSON,
deserialisation into `SearchResults<T>`, and then `AzureSearchServiceAdaptor`, the mappers and the
use case. Only the socket is replaced.

### What is not tested

The TLS handshake and the network hop. Neither was meaningfully tested before — the previous setup
validated a locally minted CA against itself.

---

## Why not a stub server?

A stub server was the original design (WireMock.Net in a container) and it cost far more than it
returned. `Azure.Search.Documents` calls `endpoint.AssertHttpsScheme(...)` in the `SearchClient`
constructor, so a plain-HTTP stub URL is rejected before any request is made. The SDK then applies
strict TLS validation, so a self-signed certificate is rejected too:

```text
System.Security.Authentication.AuthenticationException: The remote certificate is invalid because of errors in the certificate chain: UntrustedRoot
```

Satisfying both required a CA-signed certificate generated by a dedicated container, a shared
volume, `update-ca-certificates` inside the test container, and therefore a Linux runner. That is
what has been removed.

Note that overriding the transport is required by *any* container-free option — including running
WireMock.Net in-process — because there is no other way past `AssertHttpsScheme` plus certificate
validation without manipulating the OS trust store. Once the transport is ours, the socket adds
nothing, so it was dropped as well.

---

## Cost: contract parity

The stubbed payloads must be kept in step with Azure Search. Its API is versioned via `?api-version=`,
which the SDK sets. There **should** be post-deployment system tests validating against the real
service — this stub cannot tell you the real contract has changed.

## Assertions this enables

`AzureSearchIndexStub.ReceivedRequests` records every request, so tests can assert that a search was
made against a specific index, or that no search happened at all. The request body is captured too,
which makes it possible to assert on the generated `filter`, `orderby` and `searchFields`.
